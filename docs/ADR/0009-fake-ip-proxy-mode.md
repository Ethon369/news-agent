# ADR-0009：Fake-IP 代理兼容模式（默认关闭）

- 状态：已采纳
- 日期：2026-10-20

## 背景

真实链路回归时发现：本机网络使用 Clash 类代理，DNS 被接管，所有外部域名被解析为 **198.18.0.0/15（Fake-IP 段）**。我们的 SSRF 防护把该段判为「内网/保留地址」，导致 `fetch_url` 全部失败：

```
ERROR[fetch_failed]: 拒绝访问内网/保留地址: techcrunch.com -> 198.18.0.166
```

后果：Agent 无法读取正文，简报的证据分级只能停留在「仅来源摘要」。这不是代码 bug，而是「严格安全策略」与「代理型网络环境」的冲突。

## 决策

新增配置 `NEWS_ALLOW_FAKE_IP`（默认 `false`）：

- `false`（默认）：完全严格，198.18.0.0/15 视为保留地址拒绝；
- `true`：显式放行 198.18.0.0/15，**其余私网/回环/链路本地/保留地址仍然拒绝**。

代码位置：`app/news/extractor.py` 的 `assert_public_url(url, allow_fake_ip=...)`，由 `Settings.news_allow_fake_ip` 传入 `NewsService.fetch`。

## 例外说明（为什么不用「公共 DNS 重解析」方案）

对比项目（`daily-ai-news-agent`）在遇到 Fake-IP 时会向公共 HTTPS DNS 重新查询真实 IP，再固定连接并保留 TLS 证书校验——更严谨，但实现约 170 行（自定义解析、逐跳校验、连接固定）。在 3 天交付窗口内，我选择**显式开关 + 文档诚实说明**的折中：

- 默认行为不变，评审在常规网络下仍是严格的公网校验；
- 代理用户需要抓正文时，显式设 `NEWS_ALLOW_FAKE_IP=true`，并理解「此时真实目标 IP 由代理层解析，本机无法校验」；
- 其他内网段仍然被拒绝，SSRF 主防护未失效。

## 代价与残留风险

- 开启该开关后，**DNS rebinding / 代理层被劫持**场景下的防护弱于严格模式；
- 该开关只影响 `fetch_url` 的目标校验，不影响 RSS/Bing 抓取（那些走代理正常解析）；
- 生产环境建议使用方案二（公共 DNS 重解析 + 连接固定），或直接要求出口代理白名单。

## 测试

`tests/test_fake_ip.py`：

- 默认拒绝 198.18.0.35；
- 开启后放行 Fake-IP，但仍拒绝 10/127/169.254/172.16/192.168 等真实私网；
- 开启后 `fetch_article` 能正常抽取正文（MockTransport 模拟）；
- 默认模式下同一 URL 仍被拒绝。
