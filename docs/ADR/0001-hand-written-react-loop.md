# ADR-0001：手写 function-calling / ReAct 循环，而不是引入 Agent 框架

- 状态：已采纳
- 日期：2026-10-20

## 背景

题目核心要求是「工具调用顺序由 LLM 决定，不是硬编码的线性流程」，并明确允许使用 LangChain / LangGraph / Spring AI，也可以手写循环。项目时间只有 3 天，评审需要在 5 分钟内跑通并验证这一点。

## 决策

**手写一个约 200 行的 function-calling 循环**（`app/agent/loop.py`），只依赖 OpenAI 兼容的 chat completions 协议；不引入 LangChain / LangGraph。

## 理由

1. **考点就是循环本身**：评审要判断「顺序是不是模型决定的」，手写循环每一步都能指给评审看，比框架的隐藏执行更容易证明；
2. **可解释性**：轨迹（thought / tool_call / args / result）能按我们的数据结构直接落库，不需要理解框架内部事件模型；
3. **依赖更少**：框架版本迭代快，评审环境装依赖的风险更低（只多一个 `httpx`）；
4. **可控的硬边界**：`max_steps`、工具超时、结果截断、token 预算都可以在一个 for 循环里写清楚。

## 代价

- 需要自己处理：多 tool_calls 的批量返回、tool 消息格式、重试、异常、流式（本项目不做流式）；
- 未来如果要接多 Agent 编排，需要自行扩展或再引入框架。

## 备选方案

| 方案 | 放弃原因 |
|---|---|
| LangGraph | 状态机表达力更强，但本题只需要单 Agent 循环；框架会让「谁决定顺序」的论证变间接 |
| LangChain AgentExecutor | 抽象层厚，评审定位一次工具调用要跨多个类；依赖体积大 |
| 完全脚本化（不用 LLM） | 直接违反题目核心要求 |

## 后续

若将来需要多 Agent 协作（例如「选题 Agent + 写作 Agent + 事实核查 Agent」），可在此循环之上引入编排层，而不必重写工具层。
